# Static analysis: headless Ghidra + `tools/analysis`

This directory contains the Ghidra integration. The pure Python analysis
(without Ghidra) is in `tools/analysis/`. Both work on a standard AArch64 ELF
(`data/main.elf`, generated by `tools/extract/nso2elf.py`) and publish
addresses in the botw/OdysseyDecomp/viking convention: **image at
`0x7100000000`**.

Everything they produce (`tools/ghidra/out`, `tools/ghidra/projects`, `data/main_functions.csv`) is derived from the game
and is generated locally; it is not in the public repo (see docs/PUBLISHING.md).

```
tools/ghidra/
  bootstrap.py        downloads JDK 21 (Temurin) and Ghidra to tools/bin/
  analyze.py          rtti.py + analyzeHeadless + scripts + (optional) merge
  scripts/
    ApplyRttiNames.java      class namespaces, typeinfo, vtables, Class::vfN
    ExportFunctionsCsv.java  functions in viking format (+ TSV with demangle)
    ExportStringsXrefs.java  strings and imports with their references
  projects/           Ghidra projects (in .gitignore)
  out/                outputs (in .gitignore; regenerated)
tools/analysis/
  elfimage.py         ELF view: segments, symbols, relocations, pointers
  eh_frame.py         FDEs from .eh_frame (start, size)
  rtti.py             Itanium RTTI + vtables with and without RTTI -> rtti.json
  jumptables.py       switch jump tables (clang and GCC) -> targets
  coderefs.py         addresses materialized with ADRP+ADD/LDR (numpy)
  code_targets.py     all_code_targets.json + funcptrs.json (recompiler roots)
  merge_functions.py  merge of sources -> data/main_functions.csv (viking)
  demangle.py         c++filt (devkitA64/LLVM) or itanium_demangler
  tests/              tests with C++ ELFs compiled with devkitA64
```

## 1. Installation (`bootstrap.py`)

```sh
python tools/ghidra/bootstrap.py            # JDK 21 + latest stable Ghidra
python tools/ghidra/bootstrap.py --check    # shows tools/bin/toolpaths.json
pip install -r tools/analysis/requirements.txt
```

- Downloads the portable Eclipse Temurin JDK 21 (Adoptium API, with SHA-256
  verification) and Ghidra from the GitHub releases (SHA-256 from the release
  notes). Everything goes to `tools/bin/` (in `.gitignore`), and the **system
  Java is not modified** (1.8, which is no good for Ghidra):
  `analyze.py` defines `JAVA_HOME` only for the Ghidra process.
- Versions installed on 2026-10-03: **Temurin JDK 21.0.12.1+1** and
  **Ghidra 12.1.4** (about 1.2 GB on disk; the .zip files are deleted after extraction
  unless `--keep-archives` is given).
- `--ghidra-version X.Y.Z` pins another Ghidra version.

### Decision on the Switch loader

[Adubbz/Ghidra-Switch-Loader](https://github.com/Adubbz/Ghidra-Switch-Loader)
loads NSO/NRO/KIP directly. Ghidra extensions only load if they were built for the
**exact** Ghidra version, and the loader's latest build is for Ghidra 12.1.2 (the latest Ghidra is 12.1.4). Therefore:

- By default (`--switch-loader auto`) it is installed only if a build exists
  for the chosen version; otherwise it is skipped and noted in
  `toolpaths.json`.
- **We use the native ELF loader with `data/main.elf`**. We lose nothing
  relevant: the ELF carries `.dynsym`, `.rela.dyn`, `.eh_frame(_hdr)` and
  `.init_array`, which the ELF loader applies (relocations, imports,
  "GCC Exception Handlers" analyzer functions). Moreover, `main.elf` is the
  same artifact that viking and the recompiler use, so all the
  tools share addresses.
- If someone wants to open the NSO directly:
  `python tools/ghidra/bootstrap.py --ghidra-version 12.1.2 --switch-loader yes`.

## 2. Analysis with Ghidra (`analyze.py`)

```sh
python tools/ghidra/analyze.py data/main.elf                # imports and analyzes
python tools/ghidra/analyze.py data/main.elf --merge        # and updates data/main_functions.csv
python tools/ghidra/analyze.py data/main.elf --reuse        # scripts only, no re-analysis
python tools/ghidra/analyze.py data/main.elf --dry-run      # shows the command
```

What it does:
1. `tools/analysis/rtti.py` -> `out/rtti.json` (pure Python, ~2 s on PLA).
2. `analyzeHeadless` with `-processor AARCH64:LE:64:v8A -loader ElfLoader
   -loader-imagebase 7100000000` (configurable with `--base`), automatic
   analysis and Java post-scripts (compiled automatically with JDK 21):
   - `ApplyRttiNames.java out/rtti.json`: creates the class namespaces,
     labels `Class::typeinfo`, `Class::typeinfo_name`, `Class::vtable` and
     renames as `Class::vfN` (or `Class::thunkO_vfN` in secondary
     sub-vtables) the virtual functions still called `FUN_...`. Base
     classes are processed first, so an inherited function that is not overridden
     gets the name of the class that introduced it. Vtables
     without RTTI are named `vtable_<addr>`.
   - `ExportFunctionsCsv.java` -> `out/ghidra_functions.csv` (viking format,
     see below) and `out/ghidra_functions.tsv` (full name, mangled and origin).
   - `ExportStringsXrefs.java` -> `out/strings.tsv` (address, length, number of
     references, functions that use it, escaped string) and `out/imports.tsv`
     (import, number of calls, functions that call it).
3. With `--merge`, `tools/analysis/merge_functions.py` integrates Ghidra's CSV.

Memory: `--maxmem` (default 16G for ELFs > 16 MiB). Logs are in
`out/ghidra_headless.log` and `out/ghidra_scripts.log`.

## 3. Analysis without Ghidra (`tools/analysis`)

All the scripts accept `--base` (default `auto`: `0x7100000000` if the
ELF is linked at 0) and work with or without section headers: relocations
and symbols are also read from `PT_DYNAMIC`.

```sh
python tools/analysis/eh_frame.py data/main.elf --csv tools/ghidra/out/eh_frame_functions.csv
python tools/analysis/rtti.py data/main.elf -o tools/ghidra/out/rtti.json -v
python tools/analysis/jumptables.py data/main.elf -o tools/ghidra/out/jumptables.json
python tools/analysis/code_targets.py data/main.elf --out-dir tools/ghidra/out
python tools/analysis/merge_functions.py data/main.elf --rtti tools/ghidra/out/rtti.json
```

### `eh_frame.py`
Locates `.eh_frame` by section, by `PT_GNU_EH_FRAME`, by the NSO's `MOD0`
header or by searching for the `.eh_frame_hdr` signature; decodes CIE/FDE
(all the usual DW_EH_PE encodings) and returns the exact `(start, size)`
of each FDE. Checks that the number of FDEs matches the table in
`.eh_frame_hdr`. It also reads the LSDAs (`.gcc_except_table`) of FDEs with
`L` augmentation and returns the exception landing pads.

### `rtti.py`
1. Typeinfo candidates: pointer pairs `[vptr][name]` whose name is a valid
   mangled type (validated by demangling `_ZTS<name>`). The GOT is excluded.
2. Identification of `__class_type_info` / `__si_class_type_info` /
   `__vmi_class_type_info`: by the imported or local symbol of their vtable
   (in PLA they come imported from the `sdk` module via `R_AARCH64_ABS64`), by the
   own RTTI of those vtables (statically linked libc++abi without
   symbols) or, as a last resort, by the shape of the objects.
3. Bases: si (single) and vmi (flags, offset, virtual/public).
4. Vtables: slots pointing to a class typeinfo preceded by an
   `offset_to_top`; sub-vtables are grouped (multiple and virtual inheritance) and
   construction vtables (`_ZTC`) are separated thanks to the VTTs.
5. **Vtables without RTTI** (`-fno-rtti`, the case of PLA's own code):
   `[offset_to_top][0][code pointers...]` whose address point (or start)
   is materialized in code with ADRP+ADD (constructors).

`rtti.json` format (absolute addresses):
```json
{"base": "0x7100000000",
 "stats": {"classes": 3104, "with_vtable": 2456, "vtables_without_rtti": 4359, ...},
 "cxxabi_vptrs": {"_ZTVN10__cxxabiv117__class_type_infoE+0x10": {"kind": "class", "how": "imported symbol"}},
 "classes": {
   "game::Multi": {"mangled": "N4game5MultiE", "typeinfo": "0x...", "kind": "vmi",
     "bases": [{"name": "game::Derived", "offset": 0, "virtual": false, "public": true, "typeinfo": "0x..."}],
     "vtable": "0x...", "vtable_start_exact": true, "address_point": "0x...",
     "vtables": [{"address_point": "0x...", "offset_to_top": 0, "entries": ["0x...", "__cxa_pure_virtual"]}],
     "virtual_functions": ["0x...", ...],
     "construction_vtables": [{"address_point": "0x...", "for": "game::Diamond", "vtables": [...]}]}},
 "vtables_without_rtti": [{"name": "vtable_7104...", "vtable": "0x...", "vtables": [...]}]}
```

### `jumptables.py`
Backward slicing from each `br Xn`: recognizes clang's compressed tables
(`adrp/add` + anchor `adr` + `ldrb/ldrh` + `add ..., lsl #2`), the
table-relative 32-bit ones (`ldrsw` + `add`), GCC's (`sxtb/sxth #2`) and
absolute 64-bit ones. The bound comes from the `cmp` + `b.hi/b.ls/b.hs/b.lo`, from
an `and #(2^k-1)` or from a `ubfx`; if the table base was computed outside the
loop, the whole function is searched. `br`s that are not switches (tail
calls through a pointer, PLT stubs) are counted as unresolved.

### `code_targets.py` (roots for the static recompiler)
Joins FDE starts, FUNC symbols, entry/`DT_INIT`/`DT_FINI`,
`.init_array`, vtable entries (with and without RTTI), other code pointers
from data (`R_AARCH64_RELATIVE`/`ABS64`), jump table targets and exception
landing pads (the unwinder jumps to them without any reference
in the code).

`out/all_code_targets.json`:
```json
{"module": "main", "base": "0x7100000000", "link_base": "0x0", "image_size": 70586368,
 "offsets_are": "relative to module start (va - link_base); absolute = base + off",
 "counts": {"total": 193979, "functions": 159783, "eh_frame": 158886, ...},
 "targets": [{"off": 48, "src": ["eh_frame"], "kind": "function", "size": 308},
             {"off": 13136, "src": ["jumptable"], "kind": "block"}, ...]}
```
`kind` is `function` (probable function start) or `block` (internal target:
a switch `case` or a landing pad). `src` may contain `eh_frame`,
`symbol`, `entry`, `init_array`, `vtable`, `reloc`, `plt`, `jumptable` and
`landing_pad`; PLT stubs additionally carry `"import": "<symbol>"`. `out/funcptrs.json` lists each data slot that contains
a code pointer: `{"slot", "target", "origin": vtable|init_array|reloc,
"reloc": RELATIVE|ABS64|..., "class"}` (offsets relative to the module).

### `merge_functions.py` -> `data/main_functions.csv`
viking format (open-ead/nx-decomp-tools), same as
`zeldaret/botw/data/uking_functions.csv`:
```
Address,Quality,Size,Name
0x0000007100000030,U,000308,FUN_7100000030
0x00000071001a2668,U,000132,nn::async::detail::EventBasedFutureState<...>::vf0
```
- Sizes: symbol > FDE > existing CSV > Ghidra > gap up to the next
  function (without the trailing padding); there are never overlaps.
- Names: human name from the existing CSV > **mangled** symbol (viking compares
  against the symbols of the compiled ELF, which are mangled) > imported symbol
  for PLT stubs > non-generic
  Ghidra name > provisional RTTI (`Class::vfN`, `Class::thunkO_vfN`,
  `vtable_<addr>::vfN`) > `FUN_<addr>` (or empty with `--unnamed empty`).
- viking reads the CSV **without quotes**: commas in provisional names are
  replaced with `;`. Names are unique.
- The Quality column (`O`, `m`, `M`, `W`, `L`) of a previous CSV is preserved; new
  functions enter as `U`.
- `tools/ghidra/out/main_functions_named.tsv` adds the demangle and the sources.

## 4. Tests

```sh
python -m pytest tools/analysis/tests -q                       # ~3 s
RUN_GHIDRA_TESTS=1 python -m pytest tools/analysis/tests -q    # + headless Ghidra (~20 s)
python tools/analysis/tests/build_fixtures.py                  # only build the ELFs
```
`build_fixtures.py` compiles with devkitA64 (`aarch64-none-elf-g++ -fPIC -frtti
-shared`) `fixtures/hierarchy.cpp` (single, multiple, virtual diamond
inheritance, abstract class, templates, anonymous namespace),
`fixtures/switches.cpp` (switch with jump table, function pointer table) and
`fixtures/clang_jumptables.s` (dispatches with the exact shape of clang), in
five variants: `default`, `hidden` (like Switch's `main`: imported `__cxxabiv1`
RTTI), `static` (static libsupc++ without symbols) and
`nortti` (`-fno-rtti`) and `eh` (`-fexceptions`, with `fixtures/exceptions.cpp`).
The tests run on the ELFs without symbols and
compare with the original ELF's symbol table.

## 6. Known limitations

- PLA's own code is compiled without RTTI: its classes have no names;
  only their vtables (`vtable_<addr>`) and virtual functions are recovered.
- Vtables without RTTI are confirmed by ADRP+ADD; a vtable that is never
  materialized in code (eliminated constructor) is not detected. Without that
  check (`--no-coderef`) about 200 more appear, with a risk of false
  positives.
- `vtable_start_exact: false` indicates classes with virtual bases, where the
  start of the `_ZTV` symbol is estimated by walking back over the vcall/vbase offsets.
- About 100 jump tables have no explicit bound (the `cmp` is in another block);
  they are read at most up to the next table and within the function. About 12,700
  indirect `br`s are not switches (tail calls through a pointer, PLT).
- `coderefs.py` does not follow data flow: an ADRP whose register is rewritten
  before the ADD can produce false references.
- Provisional names (`Class::vfN`) do not indicate which entry is the
  destructor (D1/D0); they only reflect the position in the vtable.
- Ghidra 12.1.4's "GCC Exception Handlers" analyzer logs tens
  of thousands of `Failed to disassemble at e2...` errors with PLA's LSDAs
  (encoding `pcrel|sdata8`, 0x1c): it adds the image base twice when
  computing the landing pads. It only affects exception marking in Ghidra;
  the FDE functions are created correctly and the correct landing pads come from
  `eh_frame.py` (all 14,948 fall inside their function).
